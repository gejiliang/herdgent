# herdr 0.7.5 实测记录（2026-07-31）

> 全部为**实测**，非推断。环境：macOS，herdr 0.7.5（2026-07-21 发布），Claude Code（Opus 5），omnigent 0.7.0。
> 易变——herdr 迭代很快，`[[startup]]` 与整套 `agent start/prompt/wait` CLI 都是 0.7.5 才加的。**引用前先复核。**

## 一、herdr 能无头驱动（这是 herdgent 成立的前提）

零客户端 attach 的情况下走通：`workspace create` → `tab create` → `agent start --kind claude --pane` → 提交 → 观测 → `agent read`。`agent start` 约 3 秒返回 `interactive_ready: true`。

## 二、状态观测的三个坑

1. **裸跑 `claude` 落在会话面板首页，不是一个会话。** 在那个界面上 `agent prompt` 的文字**会被真提交**（任务确实执行并出现在面板的 Completed 列表），但 herdr 完全观测不到，报 `agent_prompt_stalled`、status 恒为 `idle`。
   → **编排层会以为什么都没发生，实际有会话在无人看管地跑。** 解法：`agent start … -- "<初始 prompt>"` 直接进会话。
2. **`herdr agent prompt` 只输入不回车**（这版 Claude Code 的会话 TUI 上）。屏幕实证：文字停在输入框里。必须补 `agent send-keys <target> enter`。

   > **已复验（当日晚，Claude Code 2.1.220）**，且**与官方文档冲突**——herdr 文档称 `agent prompt` "submits text plus encoded Enter atomically"。实测不成立：
   > 发 prompt 后 `state_change_seq` 不变、status 停在 `done`、文字可见地停在输入框；补 `send-keys enter` 后 seq 3→5、回答出现。
   > **排除了「会话列表」这个解释**：本次复验用的是 `agent start … -- "<初始 prompt>"`，屏幕显示直接进入会话且初始 prompt 正常执行，不是裸跑落在会话面板首页的情形。
   > 未证实的猜测：herdr 可能确实发了 Enter，但 Claude Code 的 bracketed-paste 把它当成字面换行吃掉了（那正是 bracketed paste 的用途）。机制不明，但现象稳定。
   > → **设计含义**：发送后必须验证 `state_change_seq` 变化，不能盲发；跨 harness 时每家都要单独验。
3. **终态是 `done` 不是 `idle`。** `agent wait --until idle` 会一直等到超时（实测等满 2 分钟）。
   → 可用循环：记下提交前的 `state_change_seq`，提交后轮询 `agent get` 直到 seq 变化**且** status ∈ {done, idle, blocked}（实测 3.3 秒收敛）。`agent wait` 没有 "since seq" 参数，去重必须自己做，否则会拿到上一轮的终态立即返回。

> 更正一处早期判断：herdr 的观测层不弱，但它按「一个 pane 一个前台会话」建模；当 harness 自己也变成会话管理器（Claude Code 的面板首页）就失灵。

## 三、重启只恢复布局，不恢复运行时 ⚠️ 最重要

| | 结果 |
|---|---|
| workspace id、`custom_name`、pane id、cwd、布局 | ✅ 存活（`session.json` 持久化） |
| `terminal_id` | ❌ 每次必变 |
| pane 里的 agent 进程 | ❌ 全被杀（server 日志 shutdown 时 `pane child exited`） |

**恢复出来的记录是幽灵**：`agent list` / `agent get` 仍报该 agent 为 `agent_status: idle` + `interactive_ready: true`，还带着旧的 `agent_session` UUID；而同一个 `pane_id` 在 `pane read` / `pane process-info` 下是 **`pane_not_found`**，`agent read` 是 `agent_not_found`。

→ **pane 侧是权威，agent 侧不是。** `bin/reconcile.mjs` 就是为此存在（实测：重启后 herdr 报 3 个 agent 全 idle，对账正确判死）。

## 四、ID 不可作主键

`HERDR_WORKSPACE_ID=w6`（pane env 注入）在同一会话存续期间就已失效——`workspace get w6` 返回 `workspace_not_found`，同一会话此时是 `wX`。`terminal_id` 重启必变。
→ 主键只能用 **harness 侧 session id**；`custom_name`（`--label`）会持久化，可作可恢复的归属标记。

## 五、环境变量是双向泄漏的

- **从 pane 里起 herdr server 会继承 `HERDR_SOCKET_PATH`**，于是"隔离实验"实际连回了 default 会话。起隔离 server 前必须 `env -u HERDR_*`。
- **server 会把自己的环境传给它起的每个 pane，再传给每个 agent。** 实测症状：被起的 claude 状态栏出现「⚠ Transcript saving is off — inherited CLAUDE_CODE_…」，会话标题串成父会话的名字。
- **反过来不通**：`HERDR_PLUGIN_STATE_DIR` 只注入插件命令，**不会传进插件启动的会话**。所以钩子必须靠显式 argv 接力状态目录（`--state-dir`）。

## 六、Claude Code `--settings` 是【合并】语义 ✅

实测双向确认：注入的 `SessionStart` 钩子执行了（marker 落盘），**同时** herdr 自己的 `SessionStart` 钩子也执行了（`agent_session.source = herdr:claude` 被填）。
→ **控制面可以经启动 argv 注入，不会把 herdr 弄瞎。** 这是 herdgent 全部设计的地基，改动注入逻辑前先复验这条。

## 七、写代码时撞到的（真机三次失败）

1. **herdr 的错误信封走 stderr、结果走 stdout。** 只读 stdout 会把合法错误误判成"输出损坏"。
2. **agent 名有约束**：小写字母开头，只含 `[a-z0-9-_]`，1–32 字符。ISO 时间戳（带大写 T/Z）直接被拒。
3. **`workspace create` 返回时 pane 还没到交互提示符**，紧接着 `agent start` 报 `agent_pane_busy`（"not an available shell"）。而且**判据不是"shell 进程存在"**——进程早就在了、屏幕上也已有提示符，herdr 仍可能说不可用。
   → 不要猜它的判据，按它的回答重试（`startAgentWhenReady`）。
4. **起 agent 失败会漏下一个空 workspace**，必须回收，否则每次失败都在用户界面里留个空壳。
5. **SessionStart 钩子在 `agent start` 执行期间就回调**——登记必须**先于**起 agent 写入，否则钩子查无此键，session id 就丢了。

## 八、herdr plugin 契约（0.7.5）

manifest 是仓库根的 `herdr-plugin.toml`：必填 `id` / `name` / `version` / `min_herdr_version`；可声明 `[[actions]]`、`[[events]]`、`[[startup]]`、`[[panes]]`（placement: overlay/popup/split/tab/zoomed）、`[[link_handlers]]`（正则 + Ctrl+click）、`[[build]]`、`[[keys.command]]`。

命令一律 **argv 数组、无 shell 展开**，注入：`HERDR_SOCKET_PATH` / `HERDR_BIN_PATH` / `HERDR_ENV` / `HERDR_PLUGIN_{ID,ROOT,CONFIG_DIR,STATE_DIR}` / `HERDR_PLUGIN_CONTEXT_JSON`（workspace/tab/pane/worktree/agent/选中文本/URL），以及按类型的 `HERDR_PLUGIN_{ACTION_ID,EVENT,EVENT_JSON,ENTRYPOINT_ID,CLICKED_URL}`。

文档原话：**「The entire Herdr CLI is the plugin API」**。

### 8.1 manifest 实测校验（`plugin link`，当日晚补测）

`herdr-plugin.toml` 之前只按文档抄、从未被校验器加载过。实测 `herdr plugin link . --disabled` **一次通过**，manifest 原样回显：

- `[[startup]]` **不需要 id/label**，只给 `command` 即合法。
- `command` 里的**相对路径按 `plugin_root` 解析**（`["node","bin/reconcile.mjs"]` 直接跑通），不必写绝对路径。
- `platforms` / `contexts` / `description` 均被接受并回显。

三条命令全部实测被真的调用（`herdr plugin log` 取回 exit_code + stdout/stderr）：

| | 触发方式 | 结果 |
|---|---|---|
| `[[startup]]` reconcile | server 启动 | exit 0，34ms |
| action `session-list` | `plugin action invoke` | exit 0 |
| action `session-start` | `plugin action invoke` | exit 0，端到端起会话成功 |

### 8.2 plugin 运行时的三个坑

1. **`plugin action invoke` 是异步的**：立即返回 `status: "running"`，**不带 stdout**。要拿命令输出只能轮询 `herdr plugin log`。编排层不能指望 invoke 的返回值。
2. ~~**CLI 触发时 `HERDR_PLUGIN_CONTEXT_JSON` 几乎是空的**~~ —— **归因错误，已更正（2026-08-01 复验）**。

   真正的条件是**有没有活跃 workspace**，与 CLI/TUI 无关。同一条 `plugin action invoke` 命令：

   | 时机 | context |
   |---|---|
   | server 刚起、一个 workspace 都没有 | 只有 `{correlation_id, invocation_source}` |
   | 有活跃 workspace | **完整**：`workspace_cwd`、`focused_pane_cwd`、`workspace_id`、`workspace_label`、`tab_id`、`focused_pane_id`… |

   与文档一致：「Missing context fields are filled from the active workspace, tab, focused pane…」。
   最初那次实测是在刚起的空 dev server 上做的，误记成了 CLI 的限制。
   → fallback 仍然要留（空 server 的情形真实存在），但**日常使用中 plugin action 会正确认到当前 workspace 的仓库**。
   （`orchestrate` action 本身已于 0.7.0 删除，见第十五节；这条对 `session-start` 等其余 action 仍成立。）
3. **`HERDR_PLUGIN_STATE_DIR` 是注入的，不是读取的**：export 它无效，herdr 一律覆盖成 `~/.local/state/herdr/plugins/<plugin-id>/`。

   > **补充（2026-08-01）：换 plugin id 不是唯一出路。** 用 herdgent 自己的变量
   > **`HERDGENT_STATE_DIR`** 就行——herdr 不认识它，也就不会覆盖，而 `lib/registry.mjs`
   > 把它排在最优先。在**起 herdr server 时**设上，它会一路传到这个 session 的
   > plugin action、worker 会话、以及全局注册的 MCP server。
   > 实测对照：dev session 的 plugin 读到临时目录里的 registry（连 startup 对账都在那张表上跑），
   > 同一时刻 default session 读到的是真表。两张表互不可见，真状态目录一个字节没被碰。

### 8.3 端到端复验（经真 plugin 路径，非手工调脚本）

`plugin action invoke session-start` → 钩子把 `pending:<slug>` 重写为 `claude:7051dd00-…`，`harness_session_id` 与 herdr 自报的 `agent_session` 一致，`transcript_path` 拿到。随后 `session stop` + 重起 server：`agent list` 照旧报 `idle` + `interactive_ready: true`（幽灵），`pane process-info` 报 `pane_not_found`，`[[startup]]` reconcile 输出 **`0 alive, 1 buried, 0 unclear`**。第三节与第六节的结论在真 plugin 路径下再次成立。

事件共 25 种可订阅（`events.subscribe` / `events.wait`），含 `pane.agent_status_changed`、`pane.agent_detected`、`pane.output_matched`、`pane.exited`——**编排可以事件驱动，不必轮询**。

插件安装自 0.7.5 起是**用户全局**的，不再按 herdr session 隔离；`plugin link --disabled` 可先挂不启用；config/state 目录按 plugin id 分。

### 9.1 native 与 SDK 两条路线的实际代价（当日晚补测，按文件名统计）

omnigent **两套都建了**。native 覆盖 11 家（claude / codex / opencode / cursor / hermes / pi / qwen / kiro / kimi / goose / antigravity），SDK 只有 claude 与 openai-agents 完整。

| | native 桥接 | SDK 路线 | 倍数 |
|---|---|---|---|
| claude | 18,090 行 | 3,324 行 | 5.4× |
| codex | 13,678 行 | 3,066 行 | 4.5× |

claude 那 18,090 行的构成——**前两项 herdgent 完全不需要**：

| 文件 | 行数 | 作用 |
|---|---|---|
| `claude_native_forwarder.py` | 5,382 | 把终端重建成 web UI 的结构化消息流 |
| `claude_native_bridge.py` | 5,301 | 大半是把 web 端输入变回终端按键 |
| `claude_native.py` | 4,944 | 主逻辑 |
| `claude_native_hook.py` | 1,141 | 钩子 |
| 其余 6 个文件 | 1,322 | state / status / executor / harness / gateway shim |

**omnigent 自己的分工就是这两条路线的定位**：polly 的 brain 用 `claude-sdk`（需要程序化控制），polly 的 workers 全用 `-native`（需要完整 harness 能力与人工接管）。GG 本机 5 个会话也全是 `claude-native-ui`。

另：omnigent 的 bridge 文档写明它**也是靠往 pane 里 send-keys 提交**的，所以第二节那个提交坑两边同源。

许可：herdr 当时是 **AGPL-3.0-or-later**（`github.com/herdrdev/herdr`），omnigent 是 **Apache-2.0**。Apache→AGPL 单向可并入，反之不行；herdgent 取 Apache-2.0 并只经 CLI/socket 与 herdr 交互。

> **更正（2026-08-05）**：herdr 自 **0.8.0** 起改为 **Apache-2.0**（上游元数据与 `brew info herdr` 均确认）。「herdr 代码不得并入本项目」的约束自该版本起不再成立；0.8.0 之前仍按 AGPL 对待。herdgent 取 Apache-2.0 的原始理由（可吸收 omnigent）不受影响。见 [`findings-2026-08-05.md`](findings-2026-08-05.md) 第一节。

## 十、Claude Code 的 MCP 注入契约（实测，2.1.220）

编排设计把 MCP 当作 orchestrator 的工具通道，以下四条是地基。用一个零依赖手写的 stdio MCP 探针 + `claude -p` 验证。

1. **`--mcp-config` 是合并语义** ✅ —— 注入后 `herdgent-probe` 与用户原有的 `nowledge-mem`、claude.ai 连接器**同时存在**。与 `--settings`（第六节）一致。
   注意 CLI 陷阱：`--mcp-config` 接受多个值，会把紧随其后的 prompt 当成第二个配置文件路径。必须写成 `claude --mcp-config <path> -p "<prompt>"`。
2. **工具调用可以跑很久** —— 实测单次调用阻塞 **300 秒**正常返回（`-p` 模式不自动后台化，是真阻塞）。文档：`MCP_TOOL_TIMEOUT` 未设时墙钟默认约 **28 小时**，stdio server **没有** per-request timer（那个 60 秒只管 HTTP/SSE/connector）。
3. **真正的约束是 idle timeout** —— stdio 默认 **30 分钟**无响应且无 progress 即中止（`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` 可调）。而 **Claude Code 会发 `progressToken`**：实测 `tools/call` 的 params 带 `_meta: {"claudecode/toolUseId": "...", "progressToken": 2}`。
   → 长等待工具可以靠 `notifications/progress` 无限续命，**不需要设计成「短超时 + 循环轮询」**。
4. **主对话超 2 分钟的调用自动后台化**（2.1.212+）—— Claude 立刻拿到 task id 继续工作，调用结算时以 task notification 送回。**这是 polly 那套 inbox 自动唤醒的原生等价物。**
   例外：subagent 的调用不后台化（只有主对话）、IDE server 不后台化、**非交互 `-p` 模式不后台化**（除非 `CLAUDE_AUTO_BACKGROUND_TASKS=1`）。阈值由 `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` 控制。

## 十一之前：agent 参数不能含换行 ⚠️ 编排必踩

`herdr agent start <name> --kind X --pane P -- <args...>` 对参数做 shell 编码检查，**含换行的参数一律被拒**：

```
invalid_agent_argument: agent arguments cannot be encoded safely for the target shell
```

逐字符实测（用不存在的 pane 触发，参数检查发生在 pane 检查【之前】，所以通过参数检查的会报 `agent_pane_not_found`）：

| 参数内容 | 结果 |
|---|---|
| 纯 ASCII 单行 | ✅ 通过 |
| 中文单行 | ✅ 通过 |
| 双引号 / 单引号 / 反引号 / `$` | ✅ 全部通过 |
| **含换行** | ❌ `invalid_agent_argument` |

→ **只有换行是问题**，其它特殊字符都能过。

**为什么这条必踩**：初始 prompt 是作为 argv 传的，而编排者写给 worker 的任务几乎必然是多行的。
单行 ASCII 的手工测试永远撞不到，一接真编排立刻全军覆没——首次端到端实测中 3 个 worker 全部因此失败。

→ 处理：`lib/worker.mjs` 把换行压成空格，并把原文另存 `<sessionDir>/task.md`，
在压平后的提示词末尾附上路径，格式丢失时 worker 可自行查阅。

## 十之二、输入框里的「幽灵文字」会骗过屏幕判读 ⚠️

端到端测试中两次看到 orchestrator 的输入框里出现**不是任何人在这个 pane 里打的文字**，
且内容与当下情境高度吻合（「派个 worker 试试」「terminate 两个 worker，顺手删掉 xv-impl 分支」）。
第一次误判为「有人 attach 上来在打字」，于是 `send-keys enter` 想帮忙提交——**两次都没有任何反应**。

真相：那是 **Claude Code 的输入历史 ghost text**。输入历史**按项目目录共享**，
所以同一个 repo 下别的会话打过的话，会以灰字出现在新会话的输入框位置。它不是输入框的真实内容，
`send-keys enter` 提交的是空输入，所以毫无反应。

对照：`agent prompt` + `enter` 一直有效——因为它真的写入了内容。

→ **编排层不能靠读屏幕判断「这个 worker 在等人输入」**，会误判成有人正在操作而不敢动它。
状态判断只认 herdr 的语义状态与 `state_change_seq`，屏幕只用于给人看和诊断。

## 十一之二、Codex 接入实测（codex-cli 0.145.0，2026-08-01）

**没有一条能从 claude 照搬。** 每一处差异都会让编排静默失败而不是报错。

| | claude | codex |
|---|---|---|
| YOLO | `--dangerously-skip-permissions` | `--dangerously-bypass-approvals-and-sandbox` |
| 配置注入 | `--settings <file>`（合并语义） | `-c key=value`（可重复） |
| **目录信任** | 无此概念 | **必须注入**，见下 |
| session id | 自装 SessionStart 钩子 | **herdr 报告**（integration v6 已装），但 `agent start` 返回时仍是 `null` |
| transcript 定位 | 钩子回填路径 | 按 uuid 找 `<CODEX_HOME>/sessions/YYYY/MM/DD/rollout-<ISO>-<uuid>.jsonl` |
| 结果提取 | 最后一条非 sidechain assistant | `event_msg` 的 `task_complete.last_agent_message` |
| **`agent prompt` 提交** | **只输入，必须补 enter** | **自动提交**（多发 enter 无害，实测 seq 不变） |
| `ctrl+c` | 中断当前轮，会话存活 | 同左 |

### 目录信任是编排的拦路虎 ⚠️

首次在一个目录起 codex 会问 `Do you trust the contents of this directory?` 并停住。
**而 herdr 把这个界面报成 `idle` 而不是 `blocked`**——编排层会以为它在待命，实际永远不动。

信任配置在 `config.toml` 的 `[projects."<path>"] trust_level = "trusted"`，且**精确路径匹配、不继承**：
`/Users/x/Workspace` 已 trusted，子目录照样问。而每个 worker 的 worktree 都是全新路径，**全都会卡**。

→ 解法：启动时用 `-c 'projects."<cwd>".trust_level="trusted"'` 注入，**不碰用户的 config.toml**。实测有效。

### 不要装自己的 codex 钩子

`~/.codex/hooks.json` 是**全局共享**的，本机上已经有 zj-radar、orca、herdr 三方的条目。
herdr 的 codex integration（v6）已经报告 session identity，直接用 `agent get` 的
`agent_session.value` 即可，herdgent 不需要也不应该往那个文件里写东西。

## 十一之三、Pi 接入实测（pi 0.82.1，2026-08-01）

三家里**最好接的一个**，但也带出一个会让 `wait` 挂死的坑（见下）。

- **herdr 报的 `agent_session` 是 `kind: "path"`**，`value` 直接就是 transcript 文件的完整路径。
  另外两家是 `kind: "id"`。→ 不用钩子、不用搜文件，直接读。
- 没有目录信任那一关，起来就干活。
- `agent prompt` **自动提交**，不用补 enter（同 codex，与 claude 相反）。
- `--session-dir` 可指定 session 存储位置 → 产物落在 herdgent 自己的状态目录，不散落。
- 没有审批门，所以 `yolo` 对它是 no-op。要限制反而得反过来做：`--tools read,grep,find,ls`
  给只读评审用工具白名单，**比「跳过权限」精确**。
- **唯一能按模型派活的 harness**：本机 18 个模型全部经 quota-proxy 由 pi 提供，
  覆盖 Anthropic / OpenAI / Google / Moonshot / 阿里 / 智谱 / DeepSeek 七家。
  真正的跨厂商评审主要靠它。
- session 文件格式：`{type:"message", message:{role, content:[{type:"text",text}]}}`，与 claude 相似。

### ⚠️ `agent start` 回来时是 idle 还是 done，决定派活基线怎么取

| harness | `agent start` 返回时 | 含义 |
|---|---|---|
| claude / codex | `idle` | 初始任务**还没跑** |
| pi | **`done`** | 初始任务**已经跑完了** |

派活基线（`dispatch_seq`）如果一律取 `agent start` 返回时的 seq：
pi 那边就是在等一个**永远不会再来**的状态变化，`wait_for_worker` 直接挂死到兜底上限。
实测现象：三家测试卡在 `read pi` 那一步十几分钟，前面十二项全绿。

herdr 的语义分得很清：**`done` = 完成且未被查看（有新产出），`idle` = 完成或等待且已被看过（没有新产出）**。
→ 所以只对 `done` 把基线退一格（`seq - 1`），`idle` 照原样。见 `lib/worker.mjs` 的 `dispatchBaseline`。

这是同一类 bug 的第三次出现（前两次见第五步与第 9 节），根源都是**「终态」不等于「这一轮的终态」**。

## 十一之四、「终态」不等于「这一轮的终态」——同一个坑栽了四次

判断 worker 是否完成，先后用过三版 seq 判据，每版都被一个新特例打穿：

| # | 现象 | 当时的判据 | 为什么破 |
|---|---|---|---|
| 1 | wait 立刻返回，read 读回**上一轮**的答复 | 只看状态 ∈ {done,idle,blocked} | 上一轮结束后就停在终态上 |
| 2 | wait **永久挂起**（卡 10 分钟） | 基线取 `sendAndConfirm` 的 `seq_after` | 极短任务在 sendAndConfirm 返回前已跑完，等「比终态更新」 |
| 3 | 三家测试卡在 read pi 十几分钟 | 基线取 `agent start` 返回时的 seq | pi 回来时就是 `done`，seq 不会再变 |
| 4 | fox 编排卡住，worker 明明答完了 | 同上，但只对 `done` 退一格 | workspace 被「看过」，终态是 `idle` 不是 `done`，补丁没覆盖 |

**根因**：`state_change_seq` 回答的是「状态变了几次」，而我们真正要问的是「**有没有新产出**」。
两者在大多数情况下同向，所以每次补丁都能撑一阵，然后被下一个特例打穿。

→ 判据换成 **transcript 里的 assistant 轮次数**：派活前记基线（新 worker 是 0，
`send_to_worker` 是发送前的值），多出一轮才算这一轮结束。
这个判据对三家 harness 一致，也不受 idle/done 之分影响。seq 只留作降级——
transcript 还没落盘的那一小段窗口里兜底。

## 十一、worktree 与取消语义（实测）

1. **worktree 的 checkout 不落在项目目录** —— `herdr worktree create --cwd <repo> --branch X` 把 checkout 建在 **`~/.herdr/worktrees/<repo>/<branch>`**。项目仓库里只多 `.git/worktrees/<name>` 元数据（git 机制必然），工作区仍 `clean`。
2. **父子分组是自动的** —— 上述命令自动建出父 repo workspace（`w1`，label 为仓库名）并把 worktree workspace（`w2`，label 取 `--label`）分在其下。**编排的物理布局不用设计，herdr 直接给。**
3. **`worktree remove` 不删分支** —— 需要额外 `git branch -D`，否则每次编排都在仓库里留一个分支。
4. **`ctrl+c` 中断当前轮，不杀会话** —— 状态 `working` → `done`，屏幕出现 `⎿ Interrupted · What should Claude do instead?`，claude 进程仍在前台，输入框可继续派活。
   → **取消必须分两层**：软中断（保留 worker 可复用）与硬终止（关 pane / workspace）。`cancel_worker` 要返回实际用的是哪种。

## 十三、Claude 模型做 agent 只能走原生通道（GG 定，2026-08-02）

网关（quota-proxy）代理的 Claude 模型**只适合简单调用**，不能拿来跑 agent。
所以 `impl-sonnet` / `review-opus` 的 harness 必须是 `claude`，绝不是 `pi`——
即便 `pi --model quota-proxy/claude-sonnet-5` 能对话（实测能，返回 OK）。

「能返回一句话」和「能当 agent 跑」是两件事。`test/profiles.mjs` 守着这条：
经 pi 的 profile 里不许出现 claude 模型。

配套的调度约束（活在 skill 里，不在代码里）：Claude 订阅是最金贵的池子，
留给评审与需求分析／设计，所以 `impl-sonnet` 只是 **fallback**——
`impl-gpt` 与 `impl-kimi` 都不可用时才派它。

## 十四、三家的只读与思考等级写法（实测 2026-08-02）

只读，都真跑过「让它创建一个文件」验证：

| harness | 参数 | 强度 | 代价 |
|---|---|---|---|
| pi | `--tools read,grep,find,ls` | 白名单 | — |
| codex | `--sandbox read-only` | 沙箱级，最硬 | 与 `--dangerously-bypass-…` 互斥（后者会关掉沙箱） |
| claude | `--allowed-tools Read Grep Glob` + `--disallowed-tools Edit Write NotebookEdit Bash` | 工具直接不存在 | **跑不了任何命令**，diff 必须喂给它 |

claude 那条为什么要连 Bash 一起禁：只禁 `Edit`/`Write` 挡不住 `echo … > file`。
禁掉之后它连 `git diff` 都跑不了，所以只读的 claude reviewer 必须配
`attach: "diff_of:<step>"`。实测报错是 `No such tool available: Write.
Write exists but is not enabled in this context.`——不是权限询问，是工具不存在。

思考等级三家的写法与档位都不同：

| harness | 参数 | 档位 |
|---|---|---|
| claude | `--effort max` | low / medium / high / xhigh / **max** —— 没有 ultra |
| codex | `-c model_reasoning_effort="max"` | low / medium / high / xhigh / ultra / **max** |
| pi | `--thinking max` | off / minimal / low / medium / high / xhigh / **max** |

只有 codex 有 `ultra`，而且它**不是**最高档。往 claude / pi 传 `ultra` 会被拒。

## 十五、`orchestrate` action 的废止（0.7.0）

它建一个独立 workspace 专门跑编排者。存在的唯一理由写在自己的注释里：

> MCP 配置只能在会话【启动时】注入，已经跑着的会话加不了工具。
> 所以编排不能在当前会话里就地开始。

装成**全局 MCP** 之后这条不再成立——任何会话开起来就带着编排工具。留着它的代价是
侧栏凭空多出一个 `orc-xxxxx` workspace，跟 worktree 容器平级，谁也说不清它算什么层级。

连带纠正的是**编排身份**：早先 root 取 harness session id（`orc:${sid}`），
于是会话一重启 root 就变，上一轮派出去的 worker 全部落在射程外——
`list_workers` 返回空数组，同时 `live_across_all_orchestrations` 显示 1，
**看得见却碰不到**。现在 root 绑 git 主仓库（`orc:repo:<path>`，
用 `git rev-parse --git-common-dir` 取，所以 worktree 里的会话算同一个项目）。
会话重启自然接手上一轮的 worker；同一项目开两个会话共享同一次编排，
并发闸一起算——它们在同一个项目里干活，本来就该互相看得见。

## 十六、worker 的代码隔离，命令不隔离（2026-08-02 实测）

第二次真编排时自己踩的：任务的验收标准里写了「真跑 `node bin/install.mjs`
验证 pi 配置生效」。worker 照做了——于是 worktree 里**还没评审**的代码
被装进了 `~/.herdgent`，覆盖掉 GG 正在用的版本（`INSTALLED.json` 的
`source` 指向 worktree、`dirty: true` 就是证据），同时写了 `~/.pi/agent/mcp.json`。

worktree 隔离的是**文件**，不是 worker 能做的事。任何写系统目录、装东西、
推远程的命令，在 worktree 里跑和在主仓库里跑效果完全一样。

→ 给 worker 的验收标准必须是**在 worktree 内自证**的：`--dry-run`、单元测试、
读配置确认格式。「装上去确实能用」归人，在合并之后做。已写进 `skills/rex/SKILL.md`。

顺带记一次成功的验证（同一次编排）：

| tab 一次建齐 | `1 impl ⋯` 与 `2 review ☐` 同时存在，review 还没开始 |
| 序号 | 1、2 连续，无重复 |
| 状态机 | `☐ → ⋯ → ✓`，impl 完成时 review 自动 `☐ → ⋯` |

## 十七、并发存活判据必须是白名单（自己踩的，2026-08-02）

修 FIXME #1 时把判据从白名单 `{starting, active}` 改成了黑名单
「不在 `{terminated, dead, failed}` 里就算 live」。当场生效的后果：早期版本留下的
`reclaimed` 记录立刻变成幽灵，`live_across_all_orchestrations` 虚报成 3，
而 registry 里一个 active 都没有。

**判据的方向不是风格问题**：
- 黑名单要求穷举**所有死法**——包括历史遗留的、以后新加的。漏一种就多一个幽灵。
- 白名单只要求穷举**活法**，而活法只有两种：登记中（starting）、agent 起来了（active）。

`status` 的取值域是封闭的，只有五个写入点（`registry.put` / agent 起来后 /
`cancel_worker` / `reconcileLive` / spawn 失败），所以白名单是完备的。

关键前提是 **`status` 与 `agent_status` 分成两格**：worker 跑完 status 仍是 active
（跑完不等于它没了，随时能派新活），herdr 报的 working/idle/done/blocked 只写
`agent_status`。混在一格里的话「done 了但还归这次编排管」就没法表达，判据也就
不可能干净。

原始缺陷从来不在判据上，在于**缺对账**：没人把 agent 已经消失的 worker 从 active
改走。修对账（`reconcileLive`）就够了，动判据是过度反应。

## 十八、⚠️ 长任务进 argv 会被截断，症状伪装成「agent 起不来」（2026-08-02 实测）

herdr 的 `agent start` 把整条命令打进 pane 的命令行。**超长会被截断**——
截断的命令引号不闭合，shell 就一直等着，agent 从没启动，herdr 等到 `--timeout`
用完报 `timed out waiting for agent startup`。

**症状具有欺骗性**：报错说的是「等待 agent 启动超时」，看起来像 agent 起得慢或起不来，
于是很容易归因成「pi 太慢，把 timeout 调大」——调大只是让它多等几分钟再报同样的错。

现场证据（一次 pi worker 的失败）：

| 事实 | 值 |
|---|---|
| 整条命令本应 | 3112 字节 |
| 命令行上实际停着 | **1023 字节**，断在中文词中间 |
| `pane process-info` 前台进程 | **zsh**（不是 pi） |
| `agent get <pane>` | `agent_not_found` |
| herdr 报的错 | `timeout: timed out waiting for agent startup` |

同一批 worker 的对照，规模与成败完全对应：

| task.md | harness | 结果 |
|---|---|---|
| 927 B | pi | ✅ |
| 1575 B | codex | ✅ |
| 2536 B | pi | ❌ |
| 2546 B ×2 | pi | ❌（早先误记为「pi 起不来」，根因就是这个） |

注意 `pane send-text` **没有**这个限制——实测发 4800 字节纯中文完好无损。
所以这是 `agent start` 那条路径独有的，不是终端或 termios 的通用上限。
确切阈值没再深挖：它可能随 herdr 版本变，而修法与阈值无关。

→ **修法：长任务只传路径，不进 argv**。任务本来就已经写进 `<sessionDir>/task.md`，
argv 里再塞一份纯属多余。阈值取保守的 1200 字节（`lib/worker.mjs` 的 `ARGV_TASK_LIMIT`）。
附带的好处是任务**不必再压平**——worker 读到的是原始格式，换行、列表、代码块都在，
比压成一行好读得多。见 `test/opening-prompt.mjs`。

这条与第十一节（agent 参数不能含换行）是同一类问题的两面：**凡是经命令行传给
agent 的东西都不可靠**，能落文件就落文件。

## 十九、⚠️ install 会当场切断运行中会话的 MCP 通道（2026-08-02 实测）

`npm run install-local` 覆盖 `~/.herdgent` 时，**正在运行的会话的 herdgent MCP server 会断连**，
编排工具当场从工具列表里消失——不是「继续用旧版」，是通道直接没了。

实测：install 完成的那一分钟，此前可用的 `mcp__herdgent__*` 全部变为 server disconnected。

**原因**：MCP server 是编排者会话的 stdio 子进程，跑的是 `~/.herdgent` 下的绝对路径。
文件被整体换掉，进程就没了。README 写的「已经开着的会话不会加载新版本，新开会话才生效」
是**弱化表述**，实际代价比那句话重。

→ **编排跑到一半绝不 install**。worker 还在跑时装新版，编排者会失去 `wait_for_worker` /
`read_worker` / `cancel_worker`，只能靠 herdr CLI 手工收场。要改代码就等本轮收尾，
或者在另一个会话里装完再开新会话编排。

这不是 bug——显式 install 步骤的目的就是让改动何时生效由人决定。但代价要记准：
**它落在正在运行的会话上，不只落在新会话上**。跟第二十一节（没有断点续跑）叠加，
中途 install 基本等于放弃本轮编排。

## 二十、容器粒度：一次编排一个 worktree，写手隔离降为 prompt 级

herdgent 的容器粒度是**一次编排 = 一个 worktree workspace + 一个分支**，
**同一次编排里所有 worker 共用这一个 checkout**（`ensureSpace()` 懒建 + 复用；
`lib/presets.mjs` 里 branch 是容器级的，不是每步一个）。

对照：omnigent 的 polly 是**每任务一个 worktree**（见 [`orchestrators-compared.md`](orchestrators-compared.md)）。

**取舍**：共用 checkout 少建少删分支，收尾负担轻——而收尾归编排者、要人工用 git / herdr
命令做（MCP 工具刻意没有任何删除动词，见第十五节与 `skills/rex/SKILL.md` 的收尾一节）。
代价是**代码隔离从结构性降为 prompt 级**：同一环节派多个写手会互相踩，唯一的防线是
`skills/rex/SKILL.md` 里那句「必须给它们互不重叠的活」。

这与 `AGENTS.md`「边界是结构性的，不是『记得过滤』」存在张力——**归属边界是结构性的，
但写手之间的隔离不是**。要真隔离就拆成多次编排（多个容器），别靠一个环节内并行。

不要与第十六节混淆：那条说的是 **worker 的代码隔离了、命令没隔离**（验收标准里不能有
「真跑一次安装／部署」）。两条是不同的边界。

## 二十一、`run_plan` 没有断点续跑，而且确定性重放本质走不通

`run_plan` / `run_preset` **没有断点续跑**。中途某个环节失败，前面烧掉的额度回不来，
只能重排。唯一的前置防护是 `missingInputs()`——在派出第一个 worker **之前**检查必填参数，
只挡得住参数缺失这一类。

**为什么不能照抄 Claude Code Workflow 的 resume**：它靠**确定性重放**——同脚本同 args 时
未改动的 `agent()` 前缀走缓存（所以它禁掉了 `Date.now()` / `Math.random()`）。
herdgent 的 worker 是**真会话**：herdr 真终端里的 claude / codex / pi 进程，
有自己的上下文和副作用，重放不出来。这条路不是「还没做」，是**本质上走不通**。
polly 同样没有断点续跑，靠 `.polly/registry.json` 当任务表。

→ **长编排先小规模试**：环节多、profile 贵的计划，先用一两步验证模板渲染和产物传递。
**验收标准写进 preset**，别指望中途纠正——中途失败的成本是整轮重来。

真要做续跑，方向是「**跳过已完成环节 + 复用已有 worker**」（registry 里已有 stage 状态和
worker slug），不是重放。注意状态是可回退的（`send_to_worker` 会把环节的 `✓` 退回 `⋯`），
设计续跑要考虑这一点。
