# herdr 0.8.0 实测记录（2026-08-05）

> 全部为**实测**，非推断。环境：macOS，herdr 0.8.0（brew，License: Apache-2.0）。
> 与 [`findings-2026-07-31.md`](findings-2026-07-31.md)（0.7.5 时代）并用；那篇里没有被本篇覆盖的结论仍有效。**引用前先复核。**

## 一、许可证：herdr 自 0.8.0 起改为 Apache-2.0 ⚠️ 旧表述全部失实

已从上游 repo `herdrdev/herdr` 的元数据确认，不只是 changelog 措辞；本机 `brew info herdr` 同样显示 `License: Apache-2.0`。

- **0.8.0 之前**的 herdr 仍然是 AGPL-3.0-or-later。引用旧版本时按 AGPL 对待。
- herdgent 与 herdr 现在**都是 Apache-2.0**，「herdr 的代码不得并入本项目」这条法律约束**已不成立**。
- herdgent 自己取 Apache-2.0 的**原始理由不变**：可以合法吸收 omnigent（Databricks, Apache-2.0）的实现思路与代码。
- **不 fork herdr 的结论不变**——理由从来都是工程成本（herdr 快速迭代，fork 长期 diverge，plugin 可分发），许可证只是曾经附带的一层约束。现在这层没了，不 fork 是**纯工程判断**。见 `AGENTS.md` 形态纪律。

## 二、两个新的可观测面（0.8.0 新发现，此前文档完全没提）

### `herdr api schema` —— socket API 的权威契约

- `herdr api schema` 给摘要，`herdr api schema --json` 给完整 JSON（约 251KB），`--output PATH` 可落盘。
- 摘要里带 **`protocol: 19`** 协议版本号。
- 价值：`lib/events.mjs` 里的事件协议形状目前完全靠实测注释固化，现在有权威来源可以对账；`protocol` 号也比 `herdr-plugin.toml` 里 `min_herdr_version` 的字符串比较更硬。

### 对账实例：`agent.read` 的参数契约（已对着 schema 核对）

新增的 socket 读取路径的参数形状，已用 `herdr api schema --json` 独立核对过（此前只对着测试自建的 fake server 验过，而 fake 不校验参数）。以下为 schema 原文：

**请求 `agent.read` → `AgentReadParams`**

| 字段 | 类型 | 约束 |
|---|---|---|
| `target` | string | **required** |
| `source` | ReadSource | **required**，枚举 `visible` / `recent` / `recent_unwrapped` / `detection` |
| `format` | ReadFormat | 默认 `text` |
| `strip_ansi` | boolean | 默认 `true` |
| `lines` | integer \| null | — |

**应答 → `PaneReadResult`**，required 字段：`pane_id`、`workspace_id`、`tab_id`、`source`、`format`、`text`、`revision`、`truncated`。

⚠️ **同一个取值在两层的拼法不同，别跨层照抄**：socket 参数用**下划线**（`recent_unwrapped`，schema 枚举），CLI 旗标用**连字符**（`--source recent-unwrapped`，见 `--help` 的 possible values）。其余三个取值（`visible` / `recent` / `detection`）两层一致，差异只在 `recent_unwrapped` 上暴露。照着 CLI help 拼 socket 请求会被 herdr 拒掉，而我们的 socket 读取路径失败是**降级静默**的（只 log 一行，功能上照常走 CLI），拼错了不会炸、只会让 `herdr_truncated` 恒为 null。`lib/events.mjs` 默认传 `visible`，不受影响。

判据：`truncated` 是 **required** 的，所以它只会在协议本身变更时缺失——`bin/mcp-server.mjs` 里那个 `typeof` 守卫和随后的降级不是防御正常情况，是防御协议变更，两条降级路径现在都会 `log()` 留痕（见 commit `97e9f27`、`9c6116e`）。

带 `command` / `event` / `exit_code` / `status` / `stdout` / `stderr`。

- 价值：`[[startup]]` 钩子（`node bin/reconcile.mjs`）跑在 herdr 启动路径上，出问题时这是**唯一**能看到它 stdout 和退出码的地方。
- 实测确认 reconcile 在 0.8.0 下跑通：`exit_code: 0`，stdout `herdgent: no active sessions, nothing to reconcile`。

## 三、两个被否掉的「坑」（看起来像，实际不是）

- **`herdr plugin` 子命令仍然存在**，只是**不出现在顶层 `herdr --help` 的摘要里**——照着顶层 help 会误以为它被删了。`install.mjs` 的 `plugin link` / `unlink` 没断。
- **`herdr worktree` 命令是 JSON-only**：0.8.0 把冗余的 `--json` 旗标从 help 和文档里撤了，但**仍然接受**它以保持兼容。我们本来就没传，不受影响。

## 四、变参 flag 吞掉 opening prompt（issue #6，已修）

**症状**：受管 claude 会话「起来了但一个 token 都没花」——herdr 报 `interactive_ready`、`agent_status: idle`、`state_change_seq` 正常，而 composer 全空、`Ctx Used: 0.0%`。编排层随后等满 30 分钟兜底上限，再把这一步**标成完成**继续往下跑。

**根因**：claude CLI 的 `--allowed-tools` / `--disallowed-tools` 是 commander 变参（`<tools...>`，见 `claude --help` 的 `Usage: claude [options] [command] [prompt]`），会吞掉其后所有非 flag 参数。herdgent 把 opening prompt 作为最后一个 argv，于是它成了又一个 tool 名。**每个 read_only 的 claude worker 必现，不是竞态**（codex 全是单值 flag、pi 的 `--tools` 是逗号串，都不受影响）。

实测（print 模式能看到交互模式静静吞掉的那句报错）：

| 命令 | 结果 |
|---|---|
| `claude -p --disallowed-tools Edit Write Bash "回答两个字：收到"` | `Permission deny rule "回答两个字：收到" matches no known tool` + `Input must be provided…` |
| `claude -p --disallowed-tools "Edit,Write,Bash" "回答两个字：收到"` | **同样被吞**——逗号串不是修法 |
| `claude -p --disallowed-tools Edit Write Bash -- "回答两个字：收到"` | 正常应答 |
| `claude -p -- "回答两个字：收到"` | 正常应答——**没有变参 flag 时 `--` 也无条件安全** |

**两条 herdr 0.8.0 契约**（隔离命名 session 实测）：

1. `herdr agent start --kind claude -- <args>` **自己前置 `claude`**，我们传的是 claude 的参数，不是完整命令行。返回的 `argv` 字段可直接核对拼出来的东西。
2. **命令里的第二个 `--` 原样透传**，herdr 不吞。这是修法成立的前提。

端到端对照（两个 pane，除了加不加 `--` 完全相同）：不加 → composer 空、零回合；加 → `⏺ 收到`。**两组在 herdr 侧的 `agent_status` 与 `state_change_seq` 完全一样**——所以「agent 起成功了」永远不能当作「任务送达了」的证据，这就是 spawn 路径必须像 `send_to_worker` 那样自己确认首轮的理由。

⚠️ **接新 harness 时必须重验自己的 flag 语义**，别照抄 `argvTerminator` 那一格。

**下游那条误导性错误**：prompt 没送达 ⇒ 没有任何回合 ⇒ Claude Code 根本不创建 transcript 文件 ⇒ 旧代码报 `transcript_unreadable: … ENOENT`，看起来像「transcript 配置坏了」（本文档记过脏 env 会关掉 transcript 的坑，恰好撞车），实际含义是「这个 agent 可能压根没开始工作」。现已改报 `no_output_yet` 并写明「若从未收到 prompt，此文件就不会存在」；`transcript_unreadable` 只留给「文件在但读不了」。

## 五、headless 恢复行为：0.8.0 修好了「幽灵 agent」，但 `process-info` 对账判据反转失效

隔离的命名 session 里起一个 claude agent，`herdr session stop` 再起同名 session，逐个接口对比：

| 接口 | 重启前 | 重启后 |
|---|---|---|
| `agent get <pane>` | `status=idle ready=true seq=1` | `agent_not_found` |
| `agent list` | 1 个 | 0 个 |
| `pane process-info` | `shell_pid=46854 fg=node,2.1.222` | `shell_pid=49548 fg=zsh`（成功返回） |
| `pane read` | 有内容 | 空 |
| workspace/pane 布局 | — | 恢复了 |
| claude 真进程 | 在 | 没了 |

**结论一：0.7.5 那个「幽灵 agent」坑，0.8.0 自己修好了。** 0.7.5 时 `agent list` / `agent get` 会把已死的 agent 仍报为 `idle` + `interactive_ready=true`，编排器会对着尸体发指令（见 `findings-2026-07-31.md`）；0.8.0 现在诚实地报 `agent_not_found`。

**结论二：以 `pane process-info` 作为对账判据反过来失效了。** 0.7.5 时死掉的 pane 报 `pane_not_found`，所以能判死；0.8.0 把 pane 恢复了（shell 起来了，见上表 `fg=zsh` 与 pid 变化），`process-info` 成功返回，于是实测 `bin/reconcile.mjs` 报 `reconcile done — 1 alive, 0 buried`，**把一个确认已死的 agent 判成了活的**（记录仍是 `status=active`）。幽灵记录会永久占用并发额度——就是 FIXME #1 治过的那个病复发。

**同一件事两处判据不一致**：`lib/worker.mjs` 的 `reconcileLive`（每次 spawn 前跑）用 `agent get`，在 0.8.0 下判对；`bin/reconcile.mjs`（startup 钩子）用 `process-info`，判错。

**教训**：对账的判据要问「这个 pane 上还有我们的 agent 吗」，不是「这个 pane 还在吗」。上游行为变了而结论没重验，就是这个仓库反复强调的那类漂移。
